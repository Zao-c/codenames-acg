# 旁观与候补调查（规则未修改）

目前 `MAX_PLAYERS=8`。`view.ts` 和 `queueForNextRound()` 都要求玩家数少于 8；开放准备阶段直接入座，锁定准备/进行中才允许候补。`promoteQueuedSpectators()` 按登记顺序挑选在线、有可恢复凭证的旁观者，跳过离线者并保留其队位；取消或明确离房会删除登记。顶部入口本轮直接使用服务端 `canQueueForNextRound` / `isQueuedForNextRound`，因此封存阶段也可准确显示资格，不改变晋升算法。

建议另立需求允许“满员提前登记，下一次安全开席时才晋升”：保留 FIFO 登记顺序，跳过离线者但保留其位置，显式取消/离房立即移除，重连沿用同一身份和队位。需进一步确认：是仅在回到准备大厅时晋升，还是允许大厅中一出空位就晋升；离线占位是否过期，以及队列是否可跨局长期保留。避免房主手动邀请与候补同时争抢最后一个席位，需要同一房间锁下校验容量。估计 1–2 个开发日及半天多人回归；这是工作量估计，尚未实施。

## 广播压力测试

脚本：`npm run test:round7:load`。独立 Node 服务、独立端口、临时 JSON/图片目录；4 玩家、20/50 个真实 Socket.IO 旁观连接，以聊天动作驱动完整 `room_state` 广播。WebSocket，单档持续约 12 秒；无断连、所有预期更新均收到。

| 旁观 | 更新/秒 | P50 / P95 / P99 ms | 单核 CPU % | 峰值 RSS MiB | JSON 传输 MiB/s |
|---|---:|---:|---:|---:|---:|
| 20 | 2 | 4 / 8 / 9 | 3.3 | 130.8 | 0.49 |
| 20 | 10 | 6 / 11 / 13 | 12.2 | 129.5 | 4.37 |
| 50 | 2 | 14 / 26 / 31 | 7.5 | 164.2 | 2.49 |
| 50 | 10 | 12 / 24 / 31 | 23.8 | 164.7 | 12.60 |

测试环境 Windows / Node 24.13.1，同机客户端与服务端；CPU 来自服务端进程累计 user+system 时间差，RSS 与事件循环延迟由测试专用 preload 采样，传输为 JSON 字节数之和，不含 WebSocket/TCP 开销。原始结果保存在本地 `output/playwright/round7/load/`。这是大厅状态广播的合成负载，不代表生产带宽、跨公网体验或含大量图片/候选作品的容量上限。

当前未证实 CPU/延迟瓶颈，因此本轮不增加人数限制或限流。高频全量广播已显示明显带宽成本：建议后续先对公共稳定作品元数据按版本缓存/复用，再评估相同权限旁观视图的编码复用或合并同步；必须保持队长/队员/旁观权限隔离，禁止把队长视图缓存发给其他身份。先测量真实线上频率与峰值，再决定是否实施，不能仅凭同机压测承诺可承载 50 人公网观战。
