# 第二批架构与任务分解

日期：2026-10-16。状态：P2-0～P2-5 已实现并随 `e21aacb` 部署（服务开关默认关闭）；P2-6～P2-8 未开始。基线 `d8db239`（应用 `219dcb3`）→ 现应用 `e21aacb`。规则差异、现网证据及未决选择见 [需求复核](PHASE2_REQUIREMENTS_REVIEW.md)。本计划按该文推荐默认值编排；实施与部署结果见 [交付记录](cipai-v2-delivery.md)。

## 1. 数据边界

维持现有 Node 单进程、Socket.IO、房间锁、独立经典/揭幕规则和 nextPlan。新能力按当前 match 存储；不把私人图挂到 nextPlan，不用公共 GameReplay 作为秘密存储容器。

建议新增以下领域类型（名称可在实施时局部调整）：

| 类型 | 关键字段与职责 |
| --- | --- |
| `MatchPrivateState` | schemaVersion、matchId、正式成员 ACL 快照、稳定主体秘密接触集合、两队图、各队长意图、私人预测、preRevealSnapshots；仅服务端模型 |
| `AssociationGraph` | graphId、revision、scope=`match` 或具体 clueId、cardId 节点、边、纯文本；作品元数据由该局棋盘解析，禁用标题作外键；布局坐标为归一化坐标 |
| `CaptainIntent` | ownerPrincipalId、team、scope、draftGraph、lockedPlan；锁定生成当前不可变计划副本，编辑另一个草稿，不覆盖锁定内容 |
| `PreRevealSnapshot` | snapshotId、matchId、clueId、cardId、单调 revealSeq、serverAt、双方相关整局/当前线索图副本、当时意图/锁定计划、有效预测副本；深拷贝、不可变 |
| `PrivatePrediction` | matchId、principalId、cardId、choice=red/blue、revision、updatedAt、冻结状态；不含可自填真值/得分 |
| `PrivateMatchArchive` | matchId、replayId（关联公共回放）、endReason、归档 ACL、快照、图、意图、干扰、个人预测评价及主动分享授权、expiresAt；独立存储/鉴权视图 |
| `AnimeCommunityPool` | id、ownerId、revision、name、description、结构化 workIds、visibility、moderationStatus、createdAt/updatedAt；管理员状态独立于作者发布状态 |

活跃私有状态可作为 Room 内显式内部字段，以便与棋盘一次提交；同时从 PublicRoomState 类型中排除，公开 DTO 使用明确字段白名单。私密历史归档独立于 Room，不能随着下一局重置而消失。公共 `buildReplay` 持续只构建公共 DTO，`/api/replays/:replayId` 永不返回 PrivateMatchArchive。

作品节点引用 **matchId + Card.id**；anime.id 仅作作品资料索引。clueId 由服务端当前提示确定。编辑请求携带 expectedRevision、requestId 和 matchId；拒绝陈旧版本，不采用整图静默覆盖。删除节点同时移除悬空边。文字按纯文本渲染，不接受 HTML。

## 2. 权限矩阵（推荐默认值，待确认）

| 身份/阶段 | 团队图 | 队长意图 | 预测 | 私密归档 |
| --- | --- | --- | --- | --- |
| 当前同队普通队员、未见秘密 | 读写本队；不读对队 | 不可见 | 不可参与 | 正常结束且命中本局 ACL 才读双方图/意图/干扰 |
| 当前队长 | 只读本队图 | 仅本人读写/锁定 | 不可参与 | 同上 |
| 卸任且见过秘密者 | 不参与实时协作；保留本人私人意图读取 | 本人历史可读，卸任后不再写 | 禁止 | 正常结束且命中 ACL 才解锁 |
| 无秘密观众 | 不可见 | 不可见 | 仅本人未翻牌红/蓝；冻结后不可改 | 正常结束只见本人预测结果及获授权分享 |
| 房主/未来队长 | 依据当前身份，不额外提权 | 同左 | 同左 | 不因房主/下局身份获得旧局权限 |
| 公共 REST/分享基础回放/陌生访客 | 无私有字段 | 无 | 无 | 只有既有基础回放 |
| 认输/中止 | 停止写入，不追加跨队解锁 | 不公开 | 不评价、不分享成绩 | 不新增揭密；原本可读的个人草稿不因终局自动扩散 |

每次动作和每次输出都由服务器重验身份、局次、阶段及秘密接触状态。正常结束 ACL 不采用当前房间晋升后的 players 列表。公共聊天室、lastEvent、调试日志不能记录私有边、文本、预测选择或私密令牌。

## 3. 翻牌事务与并发顺序

1. `guessCard` 取得现有房间锁，读取并克隆 Room；验证实际连接、身份、match、当前线索及猜牌资格。
2. 找到卡，若已翻开则沿用当前幂等返回：无第二个快照/冻结/得分。
3. 在 `card.revealed = true` **之前**，按服务端当前数据深拷贝相关图和意图，冻结该 cardId 的有效预测并分配 revealSeq。不能使用浏览器时间戳或客户端快照。
4. 执行现有翻牌、回合、计分、胜负逻辑；将翻牌结果与私有快照作为同一聚合状态一次 `setRoom`。捕获失败不提交部分更改。
5. 提交后才通知授权客户端。预测/图编辑也走同一房间锁；先取得锁的操作决定是否赶上此次快照，晚到的预测被拒绝。
6. 终局私密数据先封存于最终局状态；`ensureReplay` 在晋升候补前持久化/归档，按 matchId 幂等关联公共 replayId。归档失败不得晋升并覆盖旧私有数据，可安全重试；不重复计分。

当前 MemoryRoomStore 返回引用，所以克隆是必要步骤。不要把 public replay store 和 private store 两次写误称为数据库事务；采用稳定 matchId 的幂等归档与完成标记，发生故障可重试。若以后要求跨重启一致性，需单独设计原子落盘/恢复协议。

## 4. 通信、容量与展示

建议动作：`team_graph_edit`、`captain_intent_edit`、`captain_intent_lock`、`prediction_set` / `prediction_clear`、`prediction_share`、`private_replay_get`。名称只是接口草案；动作鉴权使用 Socket 绑定会话，忽略客户端自报 team/owner/role。私密归档 REST 若采用，必须用专用成员凭证鉴权，不能拿公开 replayId 当凭证。

编辑采用受限 patch + revision，冲突返回简洁错误和调用者有权看到的最新视图；requestId 重放不二次应用。私有改动只向有权主体发送更新，不反复广播整盘/全部候选池。连接恢复发送当前授权快照；切换队长、换队、离房和换局要清理客户端旧权限缓存。

建议初始容量预算（工程默认值，负载验收后可调）：每个图最多棋盘卡数个作品节点、128 条边、32 条文字、每段 200 字、单请求 32 KiB；每主体每秒 5 次编辑持续速率与短突发限制；每局私有聚合上限需实测序列化体积后确定。只存当前草稿与必要锁定计划，不保存每次拖动历史。快照上限随真实翻牌数（动画最多 36），内容使用稳定引用和有限文本；保存时深拷贝，不保留可变对象引用。超限有明确反馈，不悄悄丢记录。

图板默认折叠；桌面从棋盘工具入口按需展开，手机独立页/抽屉；提供“选两个作品→建立关系”的无拖拽路径、纯文本编辑和键盘操作。当前线索/整局只切换作用域，不改变棋盘猜牌动作。保留完整 6×6、单击预览、二次猜牌确认、真实 Bangumi 外链；不给预测动作复用 guess_card。延续现有深浅主题 token，不上复杂背景或长期占位的大型图板。

## 6. 社区数据补充约束

浏览器本地作品池的导入是用户主动操作，导入前展示作品数量和非法 ID；服务端按现有动画目录校验，不能把未知作品直接并入全站目录。至少满足 25/36 个不同系列才允许对应开局；公开池可以先保存较小草稿，但不可伪装为可开局。

发布、编辑、隐藏都递增版本；房间选池时保存合法作品快照和来源版本。公开详情不暴露举报人、内部审计、账号凭证。举报按主体/目标去重并限流；管理员隐藏理由可保留公开摘要，完整审计私有。收藏记录私人；不引入未要求的点赞票数、自动排行榜或复杂审核队列。

持久化沿用当前磁盘部署条件，新增独立文件/存储模块，原子写入及备份；不得覆盖现有 users.json、文字题库或图片文件。若访问量和写入冲突超出现有方式，再提独立数据库迁移方案。

## 8. 开关、部署与回滚

建议服务端独立控制关联板/私密复盘、观众预测、社区发布入口；对每局固化是否启用，关闭只阻止新局/新写入，不突然清空进行中的图、预测和已授权历史。未验收阶段默认关闭。

部署须另获后续批次授权，确认生产实际版本与私有差异，等待真实房间安全空档（本轮检查有 1 个房间，不能重启）；备份源码/构建/配置及最新用户、图库、社区数据，保留版本化私有数据。不把文件备份说成能恢复内存局。

回滚程序与数据分开：停新入口、等待已启用对局结束，在安全窗口切回完整上一版 shared/server/web；保留新用户内容，不用旧 users.json 或旧社区文件覆盖新数据。旧程序不识别的新 schema 不得直接加载；持久化私密归档如新增，应有独立兼容读取/停读策略。每个 PR 写明实际变更、验证结果、开关影响、恢复路径和下一项依赖。

## 9. 下一步与确认来源

先确认需求复核第 5 节推荐边界，优先确定干扰可见性、私密复盘受众/保存策略和社区身份方式，然后从 P2-0 / P2-1 开始。无需再讨论已完成的 UI 布局，也无需重做 G0。

此停点来自用户要求遵循的 [交接补丁第 4 节](../完整%20Agent%20衔接文档包/词牌结社_2.0_文档衔接与后续批次Agent交接.md)：**“UI 完成后先提交第二批的需求差异复核与架构/任务分解”**，以及第 3 节 **“不是自动授权 Agent 把第二/第三批未经确认的新功能也顺便开发并部署”**。这是本次续接流程，不是工具或技能额外要求。
